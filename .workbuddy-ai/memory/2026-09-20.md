## ⚠️ 发现并修复一个数据回归：选手战队名（college）丢失

### 现象
对比 `00b810a`（拉取前）与 `dc4dcd7`（拉取后）：**56 个选手的 `college` 从真实战队名变成了 `null`**
（如 김윤환 캄몬스타즈、이윤열 BGM、도재욱 뉴캣슬…）。

### 根因（两层）
1. **`syncPlayers` 只抓「本地还没有的选手」** —— 已有选手的元数据**永不刷新**，
   于是早期用详情接口抓的条目一直留着，生涯战绩也越来越旧。
   另一台机器重跑时，`players.json` 走的是**列表接口**，而列表接口的 `college_name` 恒为 null。
2. **两个接口的字段不一样**（实测）：
   - 列表 `/api/players?limit=&offset=` → 有 `college_id`，但 **`college_name` 恒为 null**（0/200 非空）
   - 详情 `/api/players/{id}` → **才有真实 `college_name`**，但它对不少 id **稳定 500**（如 player 100 신상문）
   - 而 `build-db.mjs` 是 `college: raw.college_name || null` → 列表抓来的条目全部写 null

### 我一开始搞错了方向（记录以免重犯）
先以为是「列表接口更全」，于是把 235 人全部用列表接口刷新 →
结果 `college` **全变 null，比拉取后还差**。是精确核对两个接口的 `college_name` 才定位到真因。

### 正确解法（已实现）
发现 **`/api/colleges`** 一次返回全部 13 支战队（`id` / `name` / `image_path` / `is_disbanded` / …）
→ 用它把 `college_id` 解析成名称，**稳定且只要 1 个请求**，不依赖会 500 的详情接口。

`scripts/sync.mjs` 改动：
- 新增 `fetchColleges()`：拉 `/api/colleges` 建 `id → name` 映射
- `syncPlayers()` 重写：
  - **刷新所有在册选手**（不再只补新增）→ 生涯战绩（wins/losses/last_played_on/elo）每天保持最新
  - 列表接口拿到的记录，`college_name` 为空时用 colleges 映射补齐；
    补不到再退回「原值且 `college_id` 相同」的旧值，**绝不把已知战队名冲成 null**
  - 返回值从 `added` 改为 `refreshed`（`dataChanged` 判断同步更新）
- 成本：选手列表 7 页 + 战队 1 个请求 ≈ 8 个请求，实测同步仍只要 8.8s

### 修复结果（三方对比）
| 对比基准 | 结果 |
|---|---|
| vs `00b810a`（拉取前） | 战队名一致 **85 / 86**，仅 1 人不同 |
| vs `dc4dcd7`（拉取后，含回归） | **修复了 55 个**被冲掉的战队名 |
| 生涯胜场比拉取前更新 | **17 / 86** 名选手（说明刷新确实带回了新数据） |

- 唯一例外：**player 100 신상문** 战队名 `더블비` → `null`。
  官方列表接口 `college_id=null`、详情接口 500 → **按接口为准，他当前确实没有战队**，属正常变化。
- 校验：`verify.mjs` 全 ✓（`VERIFY_DONE`）、`verify-range.mjs` 64 项 `RANGE_OK`
